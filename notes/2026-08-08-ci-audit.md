# CI audit - 2026-08-08

Audit of all continuous integration and automation configuration in this repository, with every pinned version checked against an authoritative source. Line numbers in the findings table refer to the files as they were before any change was applied.


## Summary

* The repository could not build or deploy at the start of the audit. The lockfile committed on 2026-08-07 contained 14 entries that violate the repository's own `minimumReleaseAge` supply-chain policy, so `pnpm install --frozen-lockfile` failed in CI and locally, and pnpm 11's pre-run dependency check blocked `pnpm build` as well. Resolved after confirmation by rebuilding the lockfile; see the behavior change section.
* `vitepress-auto-update.yml` has failed on every scheduled run. It set up the pnpm cache before pnpm existed, pinned Node.js 20 (below pnpm 11's minimum of 22.13), used floating action tags, and had several logic bugs. It was repaired first, and then retired after confirmation in favor of Dependabot npm coverage.
* The pinned `actions/setup-node` SHA in `deploy.yml` and `pr-linter.yml` was actually v6.0.0 while the comment claimed v5.0.0.
* All actions have been upgraded to their latest releases after reading the release notes for every major version boundary crossed. All are Node.js 24 runtime or ESM updates with no interface change that affects these workflows.
* Corrections to the prompt's fact table: `minimumReleaseAge` is `4320` (three days), not `1440` (one day). All other facts in the table were confirmed.

## Proposed changes


### Safe now (applied)

Version bumps and repairs with no change to what CI accepts or rejects. The exact edits are in the working tree diff of `deploy.yml`, `pr-linter.yml`, and `vitepress-auto-update.yml`.

* All seven actions bumped to the latest SHA-pinned releases listed above, with corrected version comments.
* `node-version-file: .node-version` replaces the hardcoded `node-version: 22` in `deploy.yml` and `pr-linter.yml`, and `node-version: '20'` in `vitepress-auto-update.yml`.
* `vitepress-auto-update.yml` repaired: pnpm version detected from `packageManager` (consistent with the other workflows), pnpm installed before `setup-node`, floating tags pinned, `timeout-minutes: 15`, a `concurrency` group, `npm-check-updates` run through `pnpm dlx` so it never lands in the pull request, compact JSON for `GITHUB_OUTPUT`, and `--no-frozen-lockfile` on the post-update install.
* `pr-linter.yml`: unused `deployments: write` removed; `pnpm install` made explicitly `--frozen-lockfile` (already the CI default, so no behavior change).
* `deploy.yml`: `timeout-minutes: 10` added to the `deploy` job.


### Behavior change (applied after confirmation)

Each item below was proposed first and applied only after the user confirmed it.

1. Lockfile rebuild. The old lockfile violated `minimumReleaseAge: 4320`, so it was rebuilt with `pnpm clean --lockfile` followed by `pnpm install`. A plain rebuild was not enough: three `^` range floors in `package.json` were themselves versions published less than three days ago, so no compliant resolution existed inside those ranges. The floors were lowered to the newest compliant releases: `vue` `^3.5.41` -> `^3.5.40` (2026-07-16), `vitepress-mermaid-renderer` `^1.1.29` -> `^1.1.28` (2026-07-15), and `vitepress-sidebar` `^1.38.0` -> `^1.36.1` (2026-05-22; 1.37.0 was also too new). VitePress itself stayed at exactly `2.0.0-alpha.12`. The ranges remain caret ranges, so the newer versions will be picked up again once they age past the policy window.
1. Check-only lint mode for pull requests. `code-format:check` (`prettier --check .`) and `md-lint:check` (markdownlint-cli2 without `--fix`) were added to `package.json`, and `pr-linter.yml` now calls them, so the job actually fails on style problems. Applying this exposed a real conflict: `.markdownlint.json` mandates asterisk bullets (`MD004`) and two blank lines above headings (`MD022`), while Prettier's Markdown defaults enforce dash bullets and single blank lines, so no file with a list could ever pass both checks (and in write mode the two tools were silently rewriting each other's output on every `pnpm lint` run). Since the repository's markdownlint config is the deliberate style authority for Markdown, `*.md` was added to `.prettierignore`; Prettier still checks every other file type. After this, both checks pass across the whole repository with no changes to any file under `docs/`.
1. `packageManager` versus `devEngines.packageManager`. The `devEngines` block was deleted and `packageManager` kept, because `packageManager` is the field the wider ecosystem reads (corepack, Dependabot, `pnpm/action-setup`, and the `jq` step in the workflows), and pnpm 11 enforces the pinned version again once the conflict is gone. Trade-off accepted: the `devEngines` block is what made npm refuse to run in this repository, and that guard is now gone.
1. During the rebuild, pnpm 11 surfaced a second latent install blocker: `sharp@0.33.5` has build scripts and no entry in the `allowBuilds` map in `pnpm-workspace.yaml`, which pnpm 11 treats as a hard error (`ERR_PNPM_IGNORED_BUILDS`). The scripts have never run in this repository (pnpm 10 ignored them silently and the site builds fine on sharp's prebuilt binaries), so `sharp: false` was recorded, matching the existing `esbuild: false` and `workerd: false` entries. This would have broken the next CI install even without the lockfile problem.


### Recommended but deferred, and then decided

1. Retire or rework `vitepress-auto-update.yml`. Decision: retired (deleted) after confirmation. With VitePress deliberately pinned to the exact prerelease `2.0.0-alpha.12`, `ncu --target minor` could never fire (stable `latest` is 1.6.4, and prereleases are excluded without `--pre`). The workflow had been repaired earlier in the audit before the retirement decision; the repairs are documented in the findings table above, and the file itself is deleted.
1. Add the `npm` ecosystem to `dependabot.yml`. Decision: applied after confirmation, with `cooldown.default-days: 7` (above the three day `minimumReleaseAge`), monthly schedule, one grouped pull request, and an `ignore` entry for `vitepress` so the deliberate pin is never touched.
1. Split `deploy.yml` permissions per job: `build` keeps `contents: read`; `deploy` gets `pages: write` and `id-token: write`. Still deferred; the current workflow-level block matches GitHub's official starter workflow, so this is optional hardening.


## Verification

Commands run on 2026-08-08 (JST) after all changes, with real results:

* `node -v` -> `v24.19.0` (expected value).
* `pnpm -v` -> `11.20.0` (matches `packageManager`); the `Cannot use both "packageManager" and "devEngines.packageManager"` warning is gone after the `devEngines` removal.
* `pnpm install --frozen-lockfile` -> exit code 0 against the rebuilt lockfile. Before the rebuild it failed with `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION` (14 entries), the same failure as deploy run 31191225667.
* `pnpm build` -> succeeds, `build complete in 17.79s`, on Node.js 24.19.0.
* `pnpm code-format:check` -> passes across the repository.
* `pnpm md-lint:check` -> passes, 0 issues in 39 files.
* `actionlint` is not installed, so the workflow files, `dependabot.yml`, and `pnpm-workspace.yaml` were parsed with `js-yaml` instead; all parse cleanly.

What could not be verified:

* A green `deploy.yml` run on GitHub. The rebuilt lockfile passes the same checks locally that the failed run 31191225667 tripped on, but the workflow itself should be confirmed by pushing these changes and watching the run, or by triggering it with `workflow_dispatch`.
* The first Dependabot npm run; Dependabot only evaluates the new ecosystem after the configuration lands on the default branch.
* The exact failure step of the historical `Auto-Update Dependencies` runs; the logs have expired (HTTP 410). The diagnosis rests on the step order and the 6 to 29 second failure durations. The workflow is deleted, so this is moot.
